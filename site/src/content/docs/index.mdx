## How a feature moves

You bring a request: a feature, a ticket, a bug. The orchestrator routes it, and each role hands the next one a document.

| Role | Writes | Who signs it off |
|---|---|---|
| product-manager | a brief, or a PRD for bigger work | you, for a PRD or a change of scope |
| designer (UI work only) | a design spec and mockups | the product-manager |
| principal-engineer | a plan, ADRs, and a task list | itself, unless it contains a major decision |
| senior-developer | code and tests, one task at a time | (every task done) |
| reviewer | a review against the acceptance criteria | you approve the release |

Bugs and chores skip all of that. The senior-developer fixes them with tests and writes a short record. [Paths and gates](/dev-team/pipeline/) explains how the team decides how much process a piece of work needs.

## Why it works this way

Nothing lives only in a chat. A role's decisions go into the workspace, so the next role, or a fresh session next week, starts from the file and not from memory. Roles run inside your own conversation by default, which costs far less than starting an agent for each one; a separate agent is used only for parallel work, an independent review, or a phase too big for the current conversation. The plugin brings no stack or tools of its own, so [your project's setup](/dev-team/getting-started/#check-what-your-project-costs) decides most of what each session costs. And every role assumes mistakes, its own included: it checks its output against the source documents before handing off, and questions an input that looks wrong instead of quietly working around it.

How much you're asked is your call. At one end you sign every gate. At the other the roles sign everything except the floor: irreversible changes, security, spending, and anything that leaves the repository. [Autonomy](/dev-team/autonomy/) has the levels.
