Once several roles run at once, the orchestrator's conversation moves too fast to follow, and the workspace documents are written for agents. The Owner board is your view instead: a private claude.ai page that shows the questions and approvals waiting on you first, then who's on what, then every piece of work in flight with its ticket, PR, state and next step.

It works under either runtime. `status.md` stays the source of truth: the board is built from it, and no role reads the board to learn the state of anything.

## Set it up

```
/dev-team:board
```

The board needs Claude Code's claude.ai artifacts (the `Artifact` and `ArtifactData` tools). The command asks for a project name, what the board should call you, a ticket link base and the repository (plus short names for other repos your work touches). It publishes the page, checks `status.md` for rows whose PRs have all merged or closed so the board doesn't start stale, and seeds the rows. It then adds an `**Owner board:** <url>` line to the dev-team section, which is what turns the board on. Running the command again republishes the latest page to the same link and keeps its data.

The page is private unless you share it. Anyone you share it with can read it, but only you can change its data, and the orchestrator writes it acting as you. Nothing secret goes on it.

## What the states mean

| State | Means |
|---|---|
| `planning` | requirements through technical design |
| `building` | being built |
| `review` | in review |
| `fixing` | fixing review findings or a failed check |
| `ready` | reviewed, checks green |
| `owner` | waiting on you, with a matching question at the top |
| `blocked` | blocked on something the team must clear |
| `queued` | not started yet |
| `held` | you said to wait. Shown muted, and nobody asks again |
| `done` | finished. It stays until you've seen it, then goes |

A question or approval appears at the top the moment it's routed to you, and disappears in the turn your answer arrives. Use `held` when you want something left alone ("leave it until I've looked") or to park an old gate. Only you take a row out of `held`.

## How it stays current

The orchestrator updates the board in the same turn as `status.md`: every status change, dispatch and question routed to you. A board that lags is worse than none, so keeping it current doesn't depend on anyone remembering.

After each board update the orchestrator records a stamp (`peer board-stamp`). If `status.md` or `status-done.md` changes after the stamp, the plugin's Stop hook sends the orchestrator's turn back to update the board first.

PRs move on their own too: they merge, fail a check, go ready. `board-drift` reads the board's rows as files, which costs almost no tokens, and lists the rows whose PR has moved on. Under the Orca runtime the watcher runs it every time it wakes. `board-drift --status` does the same for `status.md`, listing rows whose PRs have all merged or closed.
